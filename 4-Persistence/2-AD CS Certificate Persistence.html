01

Why Certificates — Credential-Agnostic Persistence

Golden/silver tickets and credential dumps all die the moment the blue team rotates the right secret. Certificate persistence does not. A valid Client Authentication certificate can be used to request a Kerberos TGT via PKINIT — and password rotations don't invalidate it. It stays good until it expires (typically ~5 years) or is explicitly revoked.

Going after the CA itself

Instead of enrolling one cert, we steal the root CA's private key. With it we can forge a client-auth certificate for any user, anytime. The killer detail: because these certs were never issued through AD CS, they don't appear on the CA's issued-certificate list, so they cannot be revoked. The only cleanup is rotating the entire root CA — which invalidates every certificate in the environment and forces a PKI rebuild.

This is TryHackMe's Persisting Active Directory room. The source material itself warns these techniques are destructive and, in real engagements, are usually simulated rather than executed. Only ever run them against systems you are explicitly authorized to test.

⚠ Gotcha #1 — use the RIGHT machine

The CA private key lives only on THMDC. Running this on THMWRK1 shows just that workstation's own computer cert (template ComputerCertificateTemplate) — not the CA. If you only see one certificate, you're on the wrong host. Confirm with ipconfig: THMDC = .101, THMWRK1 = .248.

⚠ Gotcha #2 — Kali→Windows SCP fails with "No such file or directory"

Pulling from Windows with scp administrator@<ip>:"C:\...\file.pfx" . on modern Kali fails because OpenSSH 9+ uses SFTP, which mis-parses the C: drive colon. Fix: add -O to force the legacy SCP protocol → scp -O administrator@10.200.73.248:"C:\...\file.pfx" .. In this run we sidestepped it entirely by pushing from the Windows side and pulling with certutil over HTTP.

⚠ Gotcha #4 — the two errors before it worked

KDC_ERR_PADATA_TYPE_NOSUPP (error 16) against .101 = the DC wasn't accepting PKINIT preauth yet. Fix: run gpupdate /force (nudges cert auto-enrollment / policy), then retry — that's what finally returned the TGT.

Blue Team — Why It's Near-Unremovable

  • Password rotation does nothing. The cert authenticates via PKINIT, not a password — rotating the impersonated account's credentials leaves the cert fully valid.
  • Can't be revoked. We forged it offline from the stolen CA key; it was never issued through AD CS, so it doesn't appear on the issued-certificates list. There is no serial for the blue team to revoke.
  • Only real fix = rotate the root CA. That instantly invalidates every certificate AD CS ever issued, forcing re-issuance across the whole environment — effectively a PKI rebuild.
  • The nightmare scenario: the blue team rotates krbtgt twice, clears golden/silver tickets, rebuilds the CA server... and the attacker is still running DA commands because the forged cert predates the rebuild. "Yikes."
